# SSOS-9 全体レビュー (2026-11-24)

## 0. 対象・方法

- 対象は `main` @ `d8bc026` (作業ツリー clean、追跡 243 ファイル、約 35,000 行)。
- 5 領域に分けてレビューした: カーネル/FS/CLI/ビルド、アセンブラ、リンカ・エディタ、テスト基盤、文書。
- 確度の意味: **高** = 対象行を読み、再現できるものは host で実行して確認した。**中** = コード読みのみ、または一部が推定。
- 除外: `docs/review-fix-plan.md` (2026-11-15) の実装済み項目。完了扱いだが残っているものは §5 に挙げた。
- 境界: 実機、XEiJ、MPX68K はこのレビューでは操作していない。host と QEMU の結果は実 IOCS/MFP の証拠ではない。

件数は §1 を参照。

## 2. 指摘一覧

### 2.1 カーネル (K)

#### K-01 [P1] スタック予算が管理されておらず、4 KiB stack の 3 経路が限界近い

- 場所: `ssos/os/app/cli.c:131-153`、`ssos/os/fs/*.c` の局所 `sector[1024]`、`ssos/os/module/image.c:140` (stack size の最小値 4096)。
- 問題: kernel は呼び出し元 task の stack を消費する。`show_trace` の 1 KiB 配列が `ss_cli_execute_line` に inline 化されるため、すべての builtin が入るこの関数だけで 1336 byte を使う。
- 実測 (build object の prologue。GCC 13.5.0、`-O2`。IOCS 内部の使用量は含まない):

| 経路 | kernel 側の積算 | 上限 | 余裕 |
| :--- | ---: | ---: | :--- |
| shell (mux window 含む) で `smount` | 約 3.7〜3.8 KiB (`ss_cli_execute_line` 1336 + `ss_scsi_volume_attach` 1128 + `ss_human68k_probe` 1088 + `shell_loop` 132 + 他) | 4096 | IOCS `_S_READEXT` の分のみ |
| module が file fd へ `WRITE` | 約 3.0 KiB (`ss_syscall_dispatch` 692 + `ss_fat16_writer_write` 1084 + `fat_set` 1068 + 他) | 4096 (validator の最小値) | 約 1 KiB (module 側の frame を含む) |
| `ld` の `FILE_STORE` | `main` の frame が 61316。残り 4216 から app 側の最深 472 を引くと kernel 側に約 3.7 KiB | 65532 | 約 0.7 KiB |

- 現状の app (asm 65532、edit 32768) と `smount` は XEiJ で合格している。余裕はほとんどない。
- `fat12.c:194` と `fat16_write.c:91` の `noinline` は、この問題を関数単位で回避している。
- 修正案:
  1. `show_trace` を `noinline` にするか、配列を static にする。全 builtin の frame が 1336 から約 300 に減る。
  2. volume ごとに 1 個の sector buffer を `SSStorage` 側に持ち、IOCS lock の所有者が使う。局所 `sector[1024]` と `noinline` が不要になる。
  3. `tools/mkmodule.py` に `-fstack-usage` の出力を渡し、`main` の frame と stack size の差を検査する。
  4. validator の最小 stack (4096) を引き上げるか、kernel 側の使用量の上限を契約に書く。
- 確度: 高 (frame は実測。IOCS 内部は未計測)。

#### K-02 [P2] 待ち合わせがすべて polling で、lock に所有者も待ち行列もない

- 場所: `ss_iocs_lock` (`ssos/os/app/cli_console.c:95-106`)、`input_lock` (`ssos/os/app/cli_wait.c:21-32`)、`SS9_SYS_WAIT` (`ssos/os/kernel/syscall.c:108-113`)、`ss_cli_wait_pid` (`cli_wait.c:120-144`)、非対話 `wait` (`cli.c:465-468`)、`shell_loop` の key 読み (`cli.c:756-759`)。
- 問題: どれも「flag を確認して `ss_task_sleep(1)`」の 200 Hz polling。
  - lock は取得順を保証しない。
  - 待つ task は毎秒 200 回起きる。
  - shell は idle 中も 5 ms ごとに `input_lock` と `ss_iocs_lock` を取って IOCS `B_KEYSNS` を呼ぶ。窓 3 つで毎秒 600 回の lock 取得になる。
  - kill の安全性が K-03 の flag に依存している。
- 修正案: `SSTask` に待ち行列を持つ block 状態を追加し、lock 解放、子の終了、key 到着で `ss_task_wake` する。最小段階としては、lock に所有者 field と FIFO の待ち行列を足す。
- 影響: `SSTask` の size (`SS_TCB_SIZE_VALUE` 40) が変わる。`scheduler_abi.h` の static assert と `tools/check-context.py` の更新が要る。

#### K-03 [P2] kill 保護が `process_in_syscall` の流用で、CLI `kill` に所有者検査がない

- 場所: `ssos/os/app/cli.c:545,551` (`mux_shell`)、`cli.c:587,589` (`background_builtin`)、`ssos/os/process/process.c:450-477`、`cli.c:444-450`、`syscall.c:121-127`。
- 問題:
  - kernel-entry child は、生涯にわたって syscall 用の flag を 1 にしたままにすることで kill を延期している。flag は boolean で入れ子に数えない。
  - syscall の `KILL` は子のみを許すが、CLI の `kill` はどの process でも殺せる。
  - PID 1 が守られているのは、`main_tcb` が `tcb_table` の外にいて `task_id == 0` になるから (`process.c:327-331`)。明示的な仕様ではない。
- 修正案: process に `kernel_entry`/`protected` を明示し、`ss_process_kill` に所有者 (自分の子) または root の検査を入れる。PID 1 の保護を `ss_process_kill` の先頭で明示する。

#### K-04 [P2] 終了した背景 job が `wait` まで ZOMBIE のまま残り、process table が埋まる

- 場所: `ssos/os/process/process.c:383-399`、`ssos/os/app/cli.c:747`。
- 問題: 自動回収は orphan flag の付いた zombie だけ。生きている shell の子は `wait PID` を待つ。
  - `SS_PROCESS_MAX` は 8。root と mux shell 2 つで 3 つを使う。
  - ある窓で `help&` を 5 回実行すると、全窓で spawn が「Unable to start background command.」になる。
  - native test `cli_kernel_child_slot_failure_rolls_back` (`tests/unit/test_cli_background.c:476-493`) が、この 7 回目の失敗を期待値として固定している。
- 修正案: shell ごとに job table (pid と status) を持ち、prompt 待ちで非 blocking に回収して `[1] Done` を表示する。`wait PID` は table に残した status を返す。

#### K-05 [P2] module registry の寿命が `run` の fallback と噛み合わない

- 場所: `ssos/os/app/cli.c:293-323,374-381`、`ssos/os/module/module.c:96-156,221-239`、`module.h:6`。
- 問題:
  - `run NAME` の disk fallback は module を登録したままにする。`unload` しないと slot と arena が戻らない。
  - 登録後に spawn が失敗しても、module は残る。
  - 登録済みの名前は常に registry 側が優先される。disk 上の `ASM.S9M` を置き換えても `unload` するまで古い画像が動く。
  - 同名で内容が違う画像は `SS_ERR_STATE` で拒否される。
  - slot は 8 つで、`counter` と生成物も入る。
- 修正案: 参照数 0 の DYNAMIC module を `run` 終了時に解放する (要求時読み込み)。または slot が満杯のときに参照数 0 のものを LRU で追い出す。

#### K-06 [P2] 失敗理由が `-1` / `SS_ERR_PARAM` に潰れて、利用者が原因を判別できない

- 場所: `ssos/os/module/module.c:206-216`、`ssos/os/fs/storage_system.c:20-148`、`ssos/os/app/cli.c:338-339,349,357,382,421-436`。
- 問題:
  - `ss_module_load_reader` は、読み込み失敗・画像不正・CRC 不一致をすべて `SS_ERR_PARAM` で返す。
  - `storage_system.c` の全関数が `-1` を返す。「Unable to write file.」は、空き容量不足・名前の誤り・fence・I/O エラー・reader が開いていることの、どれか分からない。
  - 「Unable to start module.」は、未登録・registry 満杯・process slot 不足・memory 不足を区別しない。
- 修正案: storage と module に小さな status enum を設けて CLI で文言に対応付ける。文言は固定文字列のままにする。

#### K-07 [P3] builtin `hello` が DYNAMIC として arena を 2 重に消費する

- 場所: `ssos/os/module/builtin.c:91-115`、`module.c:176-184,202-217`。
- 問題: `hello` は静的画像を持つのに reader 経由で読み込む。一時 buffer と registry の copy で画像 2 個分の arena が要る。`counter` は BUILTIN として登録される (`builtin.c:83-88`)。扱いが 2 つある。
- 修正案: `hello_image` を BUILTIN として登録する。`load_reader` は検証済みの buffer を registry に引き渡して copy を 1 つ減らす。

#### K-08 [P3] Timer D ISR が switch tick ごとに wakeups を 2 回実行する

- 場所: `ssos/os/kernel/preemptive/interrupts.s:124`、`ssos/os/kernel/scheduler.c:458`。
- 問題: `bsr ss_do_wakeups` の後、`ss_do_context_switch` が `ss_process_wakeups` をもう一度呼ぶ。
- 修正案: どちらかを消す。`tools/check-context.py` が QEMU 側 (`tests/qemu/pre/preempt_ctx_switch.s`) と本文を比較しているので、両方を更新する。

#### K-09 [P3] stack canary を spawn のたびに全領域に書き、`debug` は mask 下で走査する

- 場所: `ssos/os/kernel/scheduler.c:109-121,284`、`ssos/os/app/cli.c:106-112`。
- 問題: `asm`/`ld` は起動のたびに 65532 byte (16,383 word) の書き込みが要る。読むのは `debug` の `ss_stack_check` だけで、task ごとに IRQ mask 下で最大 16,383 回の loop を回す。Timer D の遅延が伸びる。
- 修正案: canary の充填を `debug` を要求された時点に限る。走査は mask の外で行う。

#### K-10 [P3] syscall 層の整形

- 場所: `ssos/os/kernel/syscall.c:57-250`、`ssos/include/ssos9/user.h`、`ssos/include/ssos9/syscall.h:41-42,84,109`。
- 問題:
  - dispatch は 190 行の switch で、検証が call ごとに手書き。
  - `user.h` は trap の定型を 8 回繰り返す。`SPAWN`/`WAIT`/`KILL`/`SLEEP`/`PROC_INFO`/`PROC_LIST`/`EXIT`/`GETPID` の wrapper がない。
  - `syscall.h:41-42` の comment は `SS9_ERR_STATE` と書いている。正しくは kernel 側の `SS_ERR_STATE`。
  - `syscall.h:84` は名前を「root-directory ASCII 8.3」とするが、実装は 16 階層までの subdirectory path を受け付ける (`fat12.c:97-116`)。
  - `SS9ProcessInfo.state` は `SS_PROCESS_*` の値をそのまま出すが、公開 header に値の定義がない。
- 修正案: 番号・handler・request size・読み書きを table にする。`ss9_trap0()` を 1 個作って wrapper を集約する。

#### K-11 [P3] init 失敗時に何も表示せず停止する

- 場所: `ssos/os/kernel/premain.c:14-18`、`ssos/os/app/cli.c:786-791`。
- 問題: `ss_init` や heartbeat task の作成に失敗すると、IRQ を mask したまま無限 loop に入る。画面に何も出ない。
- 修正案: IOCS で失敗理由を 1 行出してから止まる。

#### K-12 [P3] 未使用のコードと領域

- `ctx_level` と `SS_CTX_*` (`scheduler.h:25-28,123`)。保存 level は実装されていない。
- `ss_module_link` / `ss_module_unlink` (`module.c:351-356`)。呼び出し元がない。
- `ss_save_data_base` は 1024 byte を予約して先頭の 40 byte しか使わない (`interrupts.s:262-263`)。
- `save_interrupts` は `ss_` 接頭辞がなく、offset 0,4,8,32,36,12..20,24,28 を硬直に使う (`mfp_state.s:9-62`)。`tests/xeij/mfp_snapshot.c` と対応が取れない (D-02)。
- `image_name_length` (`module.c:40-42`)。

#### K-13 [P3] helper の重複

- `read_be32` (`module.c:44`、`image.c:19`) と同等の `be32` (`scsi.c:5`、`human68k_volume.c:8`)。`write_be32` (`process.c:23`、`module.c:49`、`builtin.c:30`)。
- `short_name` (`fat12.c:56-80`) と `make_name` (`fat16_write.c:5-29`) は同一。
- fd 空き slot の探索 (`storage_system.c:24-31,48-55`)。

- 修正案: `kernel/bytes.h` と `kernel/util.c` に集約する。

#### K-14 [P3] `debug` と `uptime` の表示内容

- `debug` の task 一覧に root shell が出ない (`main_tcb` は `tcb_table` の外。`cli.c:101-128`、`main_task.c:12-13`)。
- `uptime` は時刻ではなく heartbeat の起床回数を表示する (`cli.c:641-656`)。heartbeat task は 10 slot 中 1 つと 4 KiB の stack pool を使う。
- 要決定: heartbeat を scheduler の生存確認として残すなら、その旨を comment に書く。

### 2.2 ストレージ (S)

#### S-01 [P1・要決定] 本番が使わない MS-DOS 型 FAT16 経路が残り、QEMU/native test はその経路で動く

- 場所: `ssos/os/fs/storage.c:29-69`、`fat12.c:195-238`、`fat16_write.c:5-29,92-186,212-253,371-394`、`sector_adapter.c`。文書側は D-01。
- 問題:
  - 本番の mount は `ss_scsi_volume_attach` (`scsi_volume.c:21-51`、`human68k=1`) だけ。`ss_storage_mount` に `ssos/os` 内の呼び出し元はない。
  - QEMU t13/t14/t15 と native runner は `ss_storage_mount` (MS-DOS BPB、512 byte sector、`human68k=0`) で mount する (`tests/unit/test_cli_background.c:38-45`、`tests/qemu/pre/t14_link_run.c:51-56`)。
  - そのため edit/asm/ld の on-target 試験は、本番が通らない writer/reader を使い、Human68k writer (`fat16_write.c:255-276,340-370`) は QEMU では fd 経由で実行されない。Human68k writer の coverage は host の `test_human68k_storage.c` と XEiJ の d/e 系だけ。
- 選択肢:
  - (a) legacy 経路を削除する。kernel が約 450 行減り、`noinline` 回避と 2052 byte の frame (`ss_storage_fat_copies_match`) が消える。test は Human68k 形式の fixture に切り替える。**推奨**。
  - (b) MS-DOS mount を support 対象として残す。CLI に入口を足し、AGENTS.md と `tests/README.md` に 2 経路あることを書く。
- 影響 (a): t13〜t15、`test_cli_background.c`、`test_fat12_standalone.c`、`test_storage_integrity.c`、`fat16_image_tool.c` の fixture 作り直し (M)。
- 確度: 高。

#### S-02 [P2] 書き込み fence が永続で、解除手段も表示もない

- 場所: `ssos/os/fs/storage.c:65-69,83-84,104,119-122,137`、`ssos/os/fs/scsi_iocs.c:23`。
- 問題: 書き込みに一度失敗すると `write_failed` が立つ。解除できるのは `ss_storage_unmount` だけで、本番に呼び出し元がない。`smount` は mount 済みなら拒否する。以後は SSOS-9 を再起動するまで全書き込みが同じ「Unable to write file.」で失敗する。`docs/storage-contract.md:29` は unmount と再 mount を前提に書いている (D-14)。
- 修正案: `sumount`、または再 `smount` で fence を解除できるようにする。fence 状態を `mem` や `smount` の出力に出す。

#### S-03 [P3] FAT access の読み込み過多

- 場所: `ssos/os/fs/fat16_write.c:52-67,289-291`、`fat12.c:240-252,300-308`。
- 問題: `fat_set` は entry ごとに FAT sector の read-modify-write をする。cluster の割り当てでは `fat_set` を 2 回呼ぶ。chain の検証と読み込みは cluster ごとに FAT sector を読み直す。cluster あたり数回の余分な sector 読みになる。
- 修正案: FAT sector を 1 個 cache する。K-01 の共有 buffer と併せて設計する。

### 2.3 CLI (C)

#### C-01 [P2] `cli.c` が 796 行で、役割が混在している

- 場所: `ssos/os/app/cli.c` (全体)。
- 問題:
  - 数値の整形、行編集、12 種の builtin、mux の起動、kernel の初期化 (`ss_init`)、shell loop が 1 ファイルにある。

#### C-02 [P3] 出力が断片単位で lock を取るため、mux なしでは行の中で交錯する

#### C-03 [P3] mux の窓で `exit` すると「SSOS-9 terminated.」と表示される

- 場所: `ssos/os/app/cli.c:764-767`。
- 問題: 終わるのはその窓の shell だけ。
- 修正案: 文言を分ける。

### 2.4 リンカ・エディタ (L)

#### L-01 [P1] offset 0 以外のラベルへの `.dc.l` がすべてリンクできない

- 場所: `apps/link/fold.c:181-185`。
- 問題: ABS32 (data) で addend が 0 でないものを `LINK_ERR_FIXUP` にしている。asm は同一 object 内の参照を「section anchor + addend = label の section 内 offset」として出す (`docs/assembler-contract.md:148`)。そのため先頭以外のラベルへの data pointer が一切リンクできない。関数表 (jump table) が書けない。
- 再現 (host で確認):
  ```
          .text
  f1:     rts
  f2:     rts
          .data
          .dc.l   f2
  ```
  `asm-host` は `reloc: ABS32 symbol text addend 2` を出し、`ld` は `A.O: Relocation cannot be expressed as a data fixup: ABS32 in data at 0 targets text` で止まる。`f1` (addend 0) だけなら成功する。t14 の sample は対象 label が偶然 offset 0 なので見えていない。
- 契約: `docs/linker-contract.md:46,60-62` は「常に `S + A` を再計算」とし、ABS32 (data) に addend の制限を置いていない。`fold.c:181` の comment「fixup record carries no addend」は誤り (record は `value_offset` を持つ)。

- 確度: 高。

#### L-02 [P2] section 末尾 label への fixup を含む画像を「成功」で書き、loader が拒否する

### 2.5 アセンブラ (A)

`tests/build/asm-host` と `m68k-xelf-as` 2.46.0 (`-m68000`) に 791 形式の命令を入れて、受理と拒否、text の byte を比較した。

- 305 形式で byte が一致し、encoding の誤りは見つからなかった。index register の既定も `.l` で GAS と一致した。
- 36 形式で byte が違った。32 形式は契約で決めた差で、GAS が abs.w や moveq に縮める、数値の分岐先、`0(%an)` を `(%an)` に縮める、この GAS が `$ff` を hex として解釈しない、のいずれか。残る 4 形式が A-01 と A-03。

#### A-01 [P1] `<<` と `>>` の優先順位が GAS と C と違う

- 場所: `apps/asm/parse.c:1118-1146`。`ev_shift` は両辺を `ev_add_level` で評価するため、shift が加減算より弱くなる。
- 実測 (即値の値):

  | 式 | ours | GAS | C と GAS の解釈 |
  | :--- | ---: | ---: | :--- |
  | `#1<<2+3` | 0x20 | 0x07 | `(1<<2)+3` |
  | `#2+3<<1` | 0x0a | 0x08 | `2+(3<<1)` |
  | `#1<<2*3` | 0x40 | 0x0c | `(1<<2)*3` |
  | `#16>>1+1` | 0x04 | 0x09 | `(16>>1)+1` |

- 診断は出ず、値だけが変わる。`tests/unit/test_asm_parse.c:531` は `1+2<<2 == 12` を期待値として固定している。契約 (`docs/assembler-contract.md:23`) は優先順位を書いていない。
- 修正案: `ev_mul`、`ev_shift`、`ev_add_level` の順にして、shift を乗除と加減算の間に置く。`:531` を 9 に変え、上の 4 形式を golden に足す。契約に「C と同じ優先順位」を明記する。

#### A-02 [P1] 数値ラベルの定義が 64 件で止まる

- 場所: `apps/asm/asm.h:17` (`ASM_NUMERIC_MAX 64`)、`apps/asm/ctx.c:133-144`。
- 問題: 契約 (`docs/assembler-contract.md:18`) は「何度でも定義できる」。実装は pass 1 の定義を全件 table に溜め、65 件目で「symbol table full」になる。`ASM_LINE_COUNT_MAX` は 1200 行なので、実際の source は簡単に超える。
- 再現 (host): `1:` を 70 個置いた source が `130: symbol table full` で失敗する。64 個なら通る。
- 修正案: 次のどちらか。上限を上げるなら stack 予算 (K-01) と併せて決める。`AsmCtx` は `main` の frame にあって残りが約 9 KiB。`AsmStmt` は `AsmExpr` を 11 個持ち 2.3 KiB あるので、先に縮小する。もう一方は `Nf` を 3 パス目の走査で解くこと。

#### A-03 [P2・要決定] シフト量 0 を 1 として扱う

- 場所: `apps/asm/parse.c:1007-1008`、`docs/assembler-contract.md:23`、`tests/unit/test_asm_parse.c:508`。
- 問題: 契約に明記してあるが、GAS と C は 0 を 0 として扱う。`#1<<0` は ours が 2 で GAS が 1。`#5>>0` は ours が 2 で GAS が 5。
- 修正案: C と GAS に合わせる (推奨)。68000 命令の shift count の 0 (= 8 回) とは別の話なので、comment で区別する。維持するなら契約に理由を書く。

#### A-04 [P2] 単一レジスタの `movem` を拒否する

- 場所: `apps/asm/parse.c:578-581`、`apps/asm/encode.c:664-713`。
- 問題: `parse_reglist` に入るのは次の token が `-` か `/` のときだけ。単独のレジスタは `ASM_OP_REG` になり、`enc_movem` が「invalid operand」を返す。契約 (`docs/assembler-contract.md:24`) と `parse.c:450` の文法は単一レジスタを許す。
- 再現 (host): `movem.l %d0, -(%sp)` は ours が error で、GAS は `48e7 8000`。`movem.l %d0, 4(%a1)` と `movem.l (%a0), %d0` も同じ。
- 回避: `%d0-%d0` と書く。
- 修正案: mnemonic が `movem` のときは単独のレジスタも REGLIST として扱う。

#### A-05 [P2] `ori`、`andi`、`eori` の `%ccr` と `%sr` 宛てを拒否する

- 場所: `apps/asm/encode.c:959-984` (`enc_imm_ea`)、`encode.c:349-360` (`op_kind` が特殊レジスタを拒否)。
- 問題: `ori.b #3, %ccr`、`andi.w #3, %sr`、`eori.b #1, %ccr` が「invalid operand」。SR と CCR の bit を立てたり消したりする命令はこの 3 種。契約は `move %xx,%ccr/%sr` (`docs/assembler-contract.md:43`) にだけ触れている。
- 再現 (host): GAS は `003c 0003`、`027c 0003`、`0a3c 0001`。
- 修正案: `enc_imm_ea` で `%ccr` は `.b` のみ、`%sr` は `.w` のみを受理する。契約に追記する。

#### A-06 [P2] 既定の出力名で directory 部分が 8.3 の文字数に数えられる

- 場所: `apps/asm/assemble.c:317-338`、`apps/asm/main.c:172`。
