# 開発状況と今後のプラン

更新日: 2026-11-18

## 目的と範囲

SSOS-9 上で、複数のシェル画面を切り替えながらエディタでソースを編集し、アセンブラとリンカでビルドし、別画面で実行を確認する。Human68k `.x` の互換実行は必要としない。C コンパイラとプリプロセッサは後回しにする。既存の preemptive scheduler と CLI を基盤とする。

## 現在の Status

| 項目 | 状態と制約 |
| --- | --- |
| 起動とプロセス | Timer D による preemptive scheduler、process、S9M1 module、限定的な C Hello と外部 module の読み込みを実装済み。汎用 C runtime は未実装。 |
| FAT12 | 2HD の MS-DOS 型 FAT12 ルートから 8.3 名の module を読み込む。Human68k 固有形式の互換性は未検証。 |
| FAT16 | SCSI 上の FAT16 を最大 2 GB まで扱う。ASCII 8.3 ルート名、全体転送は最大 65536 byte、ファイル記述子の逐次読み書きは対応済み。`smount` の開始位置と任意の範囲長は明示指定で、パーティション自動検出はない。書き込みマウント時に FAT 複製の一致を検査する。 |
| 多重画面 | `mux` で 3 シェルを起動し、画面・キー入力・foreground process を分離。画面選択は F1～F3、または Ctrl-] の後に数字を使う。XEiJ自動テストでは実際に届くFキー経路を使う。80×25 の文字画面で、汎用端末制御や画面分割は未実装。 |
| 開発ツール | vi風エディタ `edit`、MC68000 アセンブラ `asm`、S9O1 リンカ `ld` をS9M1として実装。編集上限16384 byte。`asm` は GAS 互換構文で S9O1 オブジェクトを FAT16 に生成する。`ld` は複数 S9O1 から既存 loader が直接読める S9M1 実行可能 module を生成する。CLI `run` は registry/builtin 未解決時に FAT16 から module を登録して起動する。ファイル記述子による段階的な読み書きと対話コンソール ABI を実装済み。リダイレクトは未実装。 |

## 検証状況

- `source ~/.elf2x68k && make verify` は 2026-11-11 に成功。クロスビルド、ホストテスト、QEMU テストを含む。QEMU のディスク・IOCS は代役であり、実機の割り込みや IOCS 動作の検証ではない。
- エディタはホスト試験で新規作成・編集・保存・再読込、未保存終了の拒否、保存失敗時の内容保持を確認。QEMU では実際の S9M1 を実行し、FAT16 上の新規作成後、mux キーイベント `~2` → `~1` を処理して編集を継続し、置換保存する統合試験を確認。
- アセンブラはホスト試験で構文 341 件、エンコード 266 件、オブジェクト出力と既定出力名の 8.3 上限を確認。ゴールデン試験で正例 8・負例 7 の計 15 ケースの text バイト列を `m68k-xelf-as` と一致させた (負例は二重ラベル、`.equ` 重複、即値ソース、bra 範囲、lea 後置インクリメント、moveq A0、不明命令)。比較では GAS 側の定義済みシンボルへの再配置を契約のフィールド規則に折り畳み、GAS (binutils 2.46) の制約から正例は `0x` 表記と後方短分岐のみを使う。クロスビルドした asm モジュールの .text は 2026-11-12 時点で 29527 byte (上限 32768) で、S9M1 イメージと XDF を生成。QEMU では実 S9M1 `asm` が FAT16 上のソースをアセンブルし、出力をホスト結果とバイト比較した。実機での `asm` 実行は未実施。
- リンカは 2026-11-12 に `source ~/.elf2x68k && make verify` で確認 (QEMU t01〜t15 全 suite、native 45 件、asm ゴールデン 15/15、link ゴールデンの self-vector・クロス比較・負例)。クロスビルドした `ld` モジュールの .text は 8094 byte (上限 32768)。t15 で mux 3 画面による edit → asm → ld → run の通し操作と arena 復帰を確認した。実機での確認は未実施。
- mux キーイベント解析の単体試験で `~3`、`~~`、F1 イベントを確認。更新した Human68k 起動イメージを MPX68K で起動し、エディタ編集中の `~2` → `~1` 切替と、戻った後の `hello` および未保存マークの保持を確認。FAT16 への保存・再読込は MPX の実環境では未確認だが、同じ実 S9M1 とキーイベント経路を使う QEMU 統合試験で FAT16 新規作成・置換保存を確認。
- XEiJ 0.26.10.08、MC68000、12 MiB、Human68k 3.02 の HDD 起動で、専用 32 MiB FAT16 イメージの SCSI IOCS 経由マウント、新規作成、読み戻し、置換を確認。停止後に `mtype` と `fsck.fat -n` でも確認した。
- XEiJ で F1～F3 による切り替えと画面保持を確認。XEiJ では制御パイプでキー入力し、画面内容で確認した。MPX68K の過去の `~` 切替記録は現行の操作手段として案内しない。
- MPX68K の macOS 入力処理に Ctrl 状態の転送を追加した検証版で、Ctrl-C による入力行破棄と `run counter` の中断、Ctrl-] と数字による 3 画面の切り替え・表示保持を確認した。ユーザーは通常インストール版を検証版と同じものに入れ替えたと報告した。入れ替え後の通常版での操作は未確認。
- ストレージのホスト試験に 512／1024 byte セクタ、FAT 複製の不一致、範囲外の BPB、書き込み故障時のフェンスを追加した。これらを含む変更後の IOCS 経路はエミュレータ未検証。
- 2 GB の疎 FAT16 イメージで作成、逐次書き込み、読み戻し、`fsck.fat -n` をホスト上で確認。MPX68K は追加 HDD を接続できないため、変更後の IOCS 経路は未確認として受け入れた。
- MPX68K の Ctrl 対応検証版で S9M1 対話テストの文字・特殊キー、画面消去、座標指定、画面切り替え後の保持、Ctrl-C 中断を確認。バックグラウンド出力は切り替え中も進み、25 行を超えた後も連続した。入れ替え後の通常版と実機での検証は別途必要。
- 実機・実媒体、全 FAT16 ジオメトリ、電断や I/O エラー時の整合性、実キーボードの全操作は未検証。検証環境と成果物ハッシュは [tests/README.md](../tests/README.md) を参照。

## 今後のプラン

### Phase 1: 入力・ストレージ基盤

1. MPX68K の Ctrl 入力修正は検証版で Ctrl-C と Ctrl-] の動作確認済み。通常インストール版はユーザーが入れ替え済みと報告。入れ替え後の操作は未確認。
2. 対話アプリ向けキー入力・カーソル移動・画面消去と各 mux 画面への入出力を実装し、[コンソール契約](console-contract.md)を定義済み。MPX68K の検証版で実行中の画面切り替えとバックグラウンド出力を確認。
3. エディタと開発ツール向けのファイル API を実装。ファイル記述子、段階的な読み書き、置換、エラー、排他の契約を定義済み。
4. FAT16 の書き込み失敗、空き領域不足、FAT 複製、512／1024 byte セクタ、2 GB イメージをホスト・QEMU と外部 FAT ツールで検証し、障害対応を明文化済み。[現行契約と障害時の扱い](storage-contract.md)を参照。MPX68K では複数 HDD を接続できないため、更新後の IOCS 実操作は未検証。

完了条件: mux 内で対話プログラムの入力・表示・中断が安定し、ツールが必要とするファイルを作成・読み書きできる。既存テストに加え、X68000 対応エミュレータで入出力を確認する。

### Phase 2: vi に似たエディタ

1. 表示・カーソル移動・挿入・削除・保存・終了を持つ小さなエディタを S9M1 アプリとして実装する。
2. ファイル読み込み、変更状態、保存失敗の通知、領域不足時の挙動を定義する。操作範囲とファイルサイズ上限を明記する。
3. mux の一画面で編集し、別画面へ切り替えて戻った後も編集内容と画面を保つことを検証する。

完了条件: FAT16 上のソースの新規作成・編集・保存・再読込は QEMU 統合試験で確認し、MPX68K では実キーによる mux 往復切替後も未保存編集内容が保持されることを確認した。Phase 2 完了。

### Phase 3: 68000 アセンブラ

1. 対象を MC68000 整数命令とし、GAS 互換構文、アドレッシングモード、シンボル、式、疑似命令、エラー表示を[アセンブラ契約](assembler-contract.md)として定義済み。未対応の命令・疑似命令はエラーで拒否する。
2. リンカ向けのオブジェクト形式 S9O1 と relocation の契約を定め、2 パスのアセンブラを S9M1 アプリ `asm` として実装済み。作業領域はすべてスタックに置き、FAT16 上のソースから S9O1 オブジェクトを生成する。
3. 命令エンコーディングとエラーケースを `m68k-xelf-as` とのゴールデン試験で比較し、正例 8・負例 7 の計 15 ケースを確認済み。QEMU 上では実 S9M1 `asm` が FAT16 上のソースをアセンブルし、出力をホスト結果とバイト比較することを確認済み。

完了条件: エディタで保存した複数のソースから、定義済みオブジェクト形式を生成できる。ホストのゴールデン試験と QEMU の on-target 試験で生成を確認し、Phase 3 を完了。エディタとアセンブラを mux 上で組み合わせた一連の操作と、S9O1 を入力とするリンカ・実行可能 module 生成は Phase 4 に引き継ぐ。実機での `asm` 実行は未実施。

### Phase 4: リンカと実行確認

1. セクション配置、シンボル解決、relocation、未解決・重複シンボルの診断を実装する。入力は Phase 3 で契約を定義した S9O1 オブジェクトで、S9M1 の既存 loader・PIC/A5 契約に合う出力形式を設計する。
2. 複数オブジェクトを結合して実行可能 module を作り、既存 loader で起動・終了・回収する。
3. 一画面で編集、別画面でアセンブル・リンク、第三画面で実行する一連の操作を FAT16 上で検証する。

完了条件: 外部ホストのアセンブラやリンカに依存せず、対象のアセンブリプログラムを作成から実行まで通せる。

2026-11-12 に完了。`ld` は 2 パスでセクション配置・シンボル解決・relocation (PC16 折り畳し、ABS16 を A5 変位へ、CODE32/DATA32 fixup 生成) と未解決・重複・PIC 違反の診断を行い、GOT/fixup 付き S9M1 v1 を直接出力する (`docs/linker-contract.md`)。`run` に FAT16 からの DYNAMIC 登録フォールバックを追加。ホストでは `test-link-golden` が独立 mini-linker とのバイト一致と `m68k-xelf-ld` との限定 profile クロス比較を行う。QEMU t14 は on-target で asm → ld → 実行 (exit status とコンソール出力) → 回収と負例を、t15 は mux 3 画面で実 `edit` によるソース作成・保存 → `asm` → `ld` → `run` → 回収までを検証する。実機での確認は未実施。
