### 2.1 F-01 [P0] リンカ容量検査の整数ラップ

- 現状: `layout.c:152-153` の `layout->symbol_count + header.symbol_count > LINK_SYMBOL_MAX` と `pool_base + header.pool_size > LINK_NAME_POOL_MAX`、および `readobj.c:116-118` の total 計算が uint32 加算。細工した S9O1(symbol_count=0xFFFFFFFF 等)で 1+0xFFFFFFFF=0 として通過し、`layout->symbols[512+]`・pool 越え書き込みで ld モジュールのスタック(LinkImage 約48KB 等)を破壊する。text/data のラップは `lk_reader_skip` が EOF で失敗するため無害(シンボル/pool 経路のみが穴)。
- 修正方針:
  1. `readobj.c` の `lk_obj_header` で各フィールドを個別上限で検証(text/data/bss ≤ LINK_*_MAX、symbol_count ≤ LINK_SYMBOL_MAX、reloc_count ≤ 上限、pool_size ≤ LINK_NAME_POOL_MAX)。total 計算は uint64 化またはフィールド上限で自明化。
  2. `layout.c:152-153` を減算形へ: `header.symbol_count > LINK_SYMBOL_MAX - layout->symbol_count` 等。二重防御として残す。
- 検証: `tests/unit/link_host_main.c` に wrap ヘッダの S9O1 を渡す回帰テスト(拒否と status 種別を assert)。QEMU 不要。
- 備考: image.c(ロード側)は多重防御済みで、links 側だけが穴という非対称を解消する位置づけ。

### 2.2 B-01 [P1] ブートサイズ契約の一元化

- 現状: IPL(`boot/main.s:49`)は $010000 から 207セクタ=211,968B(末尾 **$43C00**)までしか読まない。一方 `linker.ld:8` は RAM ORIGIN=$40000 LENGTH=80K を許可し、`makedisk` は OS バイナリを無検査で全量書く。.data が 15,360B($3C00)を超えると末尾未ロードのまま起動する(現行 .data は 12B)。
- 修正方針:
  1. `linker.ld` に `ASSERT(LOADADDR(.data) + SIZEOF(.data) <= 0x43C00, "kernel .data exceeds IPL load span (207 sectors from 0x010000)")` を追加。定数は導出コメント付きで。
  2. `makedisk` に OS バイナリ ≤ 211,968 の検査(リンカを迂回する運用の保険)。
  3. `boot/main.s:47` のトラック範囲コメント(track 1-13 → track 1-12)を訂正。
- 検証: 意図的に .data を肥大させたビルドでリンクが ASSERT で落ちること、makedisk が過大イメージを拒否すること。

### 2.4 F-02 [P1] Human68k 小文字名エントリの不可視

- 現状: `fat12.c:153-155` は `e[12..21]` に非ゼロがあるエントリをすべてスキップ。実 Human68k は 0x0C-0x0D にケースフラグを置くため、小文字を含む名前(readme.txt 等)の一般的なファイルが不可視になる。86行の「case-insensitively match」コメントと矛盾。host テストはケースバイト=0 のエントリしか作らないため検出されない。
- 修正方針: スキップ条件を **e[14..21](18+3 拡張名)非ゼロのみ** に狭め、e[12..13](ケースフラグ)は照合無関係として受理。併せて `fat16_write.c` のエントリ生成が 0x0C-0x15 をゼロ初期化していることを確認(SSOS 作成ファイルの往復安定性)。
- 前提: バイト配置は公式資料にないため、**実 Human68k 生成イメージでの確認を先頭ステップ**とする(§3 X-03)。確認後に host fixture へ昇格(小文字名・18+3 名の両ケース)。

### 2.5 F-03 [P1] FAT ミラー不更新 + マウント検証迂回

- 現状: `fat16_write.c:50` `fat_set` は `v->human68k ? 1u : v->fat_count` で 第2 FAT以降を更新しない。本番唯一のマウント経路 `ss_scsi_volume_attach`(`scsi_volume.c:36-46`)は `ss_storage_mount` の FAT 一致検査を迂回して構造体を手埋めする。Human68k 側で FAT1 が選ばれ修復されると、SSOS 割当クラスタのクロスリンク(データ破壊)になり得る。
- 修正方針:
  1. `fat_set` を human68k ボリュームでも全 FAT コピーへ書込(SCSI 書込量が増えるが正確性優先)。
  2. Human68k専用probeと解析結果（領域境界、`human68k`、`fat_big_endian`）を維持する。DOS BPBを解析して `human68k=0` とする `ss_storage_mount` への単純置換は行わない。解析済みボリュームの境界・FATコピー一致・storage初期化の検査を共通化し、両マウント経路から呼ぶ。不一致媒体は書込可能にせず、まずアタッチ拒否とする。読み取り専用提供は別途設計する。
- 検証: `test_storage_integrity.c` に「不一致 FAT ボリュームのアタッチ拒否」「書込後両 FAT 一致」に加え、Human68k属性・エンディアン・区画オフセットの保持、第2 FAT書込途中の失敗と以後の書込拒否を追加。部分失敗は原子的更新ではなく、不一致媒体を残し得ることを契約に記す。
- 備考: Human68k が FAT1/FAT2 をどう選ぶかは実機確認事項(§3 X-03)。全コピー書込にすれば選択は問わなくなる。

### 2.6 K-01 [P1] 孤児ゾンビによるスロット枯渇

- 現状: 親死亡で ROOT_PID へ reparent(`process.c:518-521`)するが、ゾンビを消費する `ss_process_wait` は呼び出し元から見て自分の子のみで、ルートシェルの shell_loop は孤児を走査しない。mux サブシェル exit 後の背景ジョブが孤児化して ZOMBIE 滞留し、`SS_PROCESS_MAX=8` を順次消費する。
- 修正方針: reparent時に孤児由来を内部フラグ等で保持し、元からrootの子だったプロセスと区別する。内部APIは孤児由来のZOMBIEだけを回収し、通常の子に対する明示的waitの終了結果を保持する。フラグはスロット再利用時に初期化し、状態更新・回収は既存の排他規約に従う。
- 呼出し位置: shell_loopとstart_muxだけに依存せず、rootが入力待ち・前景ジョブ待ち中でも進む回収経路を設計する。既存reaperとの責務を確認してから実装する。ユーザーABI拡張は不要。
- 検証: `test_cli_background.c` に「サブシェル exit → 背景ジョブ終了 → スロット回収」、入力待ち中の回収、通常の子のwait結果保持、繰返し起動でのスロット再利用の回帰を追加。
- 緩和要素(現状): ユーザーが pid を知れば `wait PID` で手動回収可。

### 2.7 T-01 [P1・基盤] 本番 ISR の同期チェック未接続・未比較

- 現状: QEMU suite は hand-copy(`tests/qemu/pre/preempt_ctx_switch.s`)のみをリンクし、本番 `ss_timerd_handler`/`ss_context_switch` は実行も比較もされない。唯一の同期チェック `tools/check-context.py` は (a) 比較ラベルにこの2つを含まない (b) `make test`/`make verify` のどこからも実行されない。本番 ISR を壊しても QEMU suite は緑のまま。
- 修正方針:
  1. `tests/Makefile` の `test`(または `verify`)から `check-context.py` を実行(1行追加)。
  2. 現行 `block()` は次のローカルラベルで停止するため、ラベルの追加だけでは不十分。`ss_context_switch` と `ss_timerd_handler` の関数全体または全基本ブロック（`.no_switch`、`.no_switch_full`を含む）を比較し、分岐先・ラベルの欠落や空の抽出結果も失敗にする。
  3. EOI差分は期待するアドレス・命令列・出現数を明示して限定的に正規化する。任意のI/O命令を除外しない。各ブロックの命令改変・ラベル削除・EOI改変でチェックが失敗する回帰を追加する。
  4. 中期: 共通部の include 一本化(本プランの範囲外にするか、余裕があれば)。
- §1 S-1/S-2 で本番ハンドラの MFP 手続きは仕様適合と確認済みのため、同期の自動保証を追加する。ただし静的比較は本番MFP割込みや実非同期タイミングの検証を代替しない。

### 2.8 K-02 [P1] `syscall_entry.s` の `tst.l` → `tst.w`

### 2.9 UI-01 [P2] B_CONSOL 列数・開始オフセット対応(仕様確定済み)

- 仕様(§1 S-3): columns=(d2>>16)+1(≤128)、rows=(d2&0xffff)+1(≤64)、開始オフセット d1=X/8+Y*128。
- 修正方針: `ss_cli_console_region` で列数も取得し mux 幅(`SS_MUX_COLUMNS=80` 固定)を `min(80, columns)` へ。開始オフセット≠0 は現行 mux の描画モデルが絶対座標 0,0 前提のため、当面は「サポート外」を明示(警告表示)し、行数は既存どおり可変。rows>31 の黙って 25 落ちも境界挙動を明示。
- 検証: `test_mux.c` で B_CONSOL スタブ戻り値を差し替えた 80列未満/オフセット付きケース。
- 備考: 661034d の「ライブ領域からのサイズ決定」の続きとして位置づけ。

## 3. 実機・エミュレータ確認タスク(コード修正と並行)

いずれも AGENTS.md の検証境界の外側。環境と記録を明示すること(docs/emulator-remote-operation.md の手順)。

- **X-01 [XEiJ] 初期スタック範囲の確認(S-4)**: 先に例外ベクタ、IOCSワーク、起動コード、使用中スタック等の領域を静的に列挙し、未使用と確認できたスタック候補範囲だけを計測用に埋める。$010000未満の一括埋めは禁止。現在使用中のスタックも上書きしない。init終了時だけでなく、代表的なIOCS呼出し・割込み・CLI負荷の後で最低到達位置を記録する。環境・ROM版・対象範囲・負荷・余裕を明示し、観測範囲内の結果として `entry.s` のコメント根拠にする。実測だけで最大使用量や全機種の安全性を保証しない。設定・媒体のバックアップと失敗時の復元手順を準備してから実行する。

## 4. 実施順序

優先度は障害の影響、実施順は依存関係と検証基盤で決める。実装段階は該当回帰と `make verify` を完了条件とし、実機依存は§3の記録を別に要求する。調査段階は根拠・再現条件・判断の記録を完了条件とする。文書のみの変更にはビルドを要求しない。commitはユーザーの明示指示時だけ行う。

1. **最優先の破壊防止**: F-01。R-10の関連する上限検査もここで確認する。
2. **検証基盤・即効の障害修正**: T-01、B-01+B-02、K-02、E-01、T-03。T-01は以後のカーネル変更より先に完了する。
3. **P1の再現と設計**: K-01、R-01〜R-03。候補の障害経路を確定し、確認されたP1修正を進める。
4. **媒体仕様とデータ整合**: X-03 → F-03、F-02、R-07。専用媒体解析を保持して共通検査を追加する。全コピー書込の前にHuman68k仕様を確認し、調査待ちの間は他の独立項目を進める。
5. **P2の契約・堅牢性**: FS-04、UI-01、A-02、T-02、R-04〜R-11の残項目。ABI変更は互換性確認後に行う。A-01は先行調査 → 方針決定 → 実装の順とする。
6. **P3の整理・任意改善**: R-12〜R-14。CRC32高速化は正確性修正と分離する。

X-01は静的な対象範囲確認を先行し、安全な測定手順が確定してから実行する。X-02とS-5のステータス仕様確認は独立した調査として進める。いずれもコード修正やQEMUのPASSで完了扱いにしない。
